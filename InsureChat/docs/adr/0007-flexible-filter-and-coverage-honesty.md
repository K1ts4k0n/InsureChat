# 0007 — filter_packages ยืดหยุ่น (limit/sort) + grounding ความซื่อสัตย์เรื่องความคุ้มครอง

**บริบท:** เดิม `filter_packages` ตัด shortlist ไว้ที่ 3 แผน เรียงเบี้ยถูกสุดเสมอ (hardcode `ShortlistSize=3`). พบจาก transcript จริงว่า: (1) ลูกค้าขอ "แผนทั้งหมด/4 แผน" ซ้ำ 3 ครั้งแต่บอททำไม่ได้ ขอโทษวน; (2) **อันตรายกว่า** — แผนเดียวที่คุ้มครองน้ำท่วมเป็นแผนเบี้ยแพงสุด ไม่ติด top 3 จึงถูกซ่อน แล้วบอทไปพูดว่า "ทุกแผนไม่คุ้มครองน้ำท่วม" ซึ่งเป็นเท็จ → ผิด grounding + เสี่ยง mis-selling (คปภ.)

**มติ:** ทำให้ `filter_packages` ยืดหยุ่น + เพิ่ม grounding เรื่องความคุ้มครอง

- **`limit`** (int, ดีฟอลต์ 3): "ขอทั้งหมด" → LLM ส่งเลขสูง backend **clamp = `min(limit, matched, 10)`**. HardCap 10 เพราะ candidate set อาจใหญ่ (40+) การเทลงแชตอ่านไม่ไหว และการบังคับให้ลูกค้าแคบลงคือพฤติกรรม consultative ที่ถูกต้องอยู่แล้ว — ถ้า matched เกินที่แสดง tool คืน note "แสดง X จาก Y บอกเกณฑ์เพื่อแคบลง"
- **`sort_by`** (enum): `premium_asc` (ดีฟอลต์), `sum_desc`, `coverage_desc` (มีไฟไหม้+น้ำท่วมก่อน) — ทิศทางผูกกับความหมาย ทุกแบบ tie-break ด้วยเบี้ยถูกสุด
- **`coverageInSet`** ในผล tool: นับความคุ้มครองจาก candidate **ทั้งชุด** เช่น `{fire:3, flood:1}` — grounding ที่ "สดและใกล้" ก่อน LLM พูด (เชื่อถือได้กว่า candidate summary ใน system prompt ที่อยู่ไกลและทำให้ดริฟต์)
- **กฎเหล็กใน prompt:** ห้ามอ้าง "ไม่มี/ทุกแผนไม่คุ้มครอง X" เว้นแต่ `coverageInSet` = 0 จริง; ถ้ามีในชุดแต่ไม่อยู่ในแถวที่แสดง → ต้องเสนอ ("มี 1 แผนคุ้มครองน้ำท่วมนะคะ อยากดูไหมคะ?")

**ทำไมไม่แก้ที่ LLM อย่างเดียว:** บอทดริฟต์เพราะความจริงเรื่องความคุ้มครองอยู่ "ไกล" ใน system prompt — ย้ายมาไว้ในผล tool (สด ใกล้จุดที่ LLM พูด) คือฟิกซ์เชิงโครงสร้าง ไม่ใช่แค่เตือนใน prompt
